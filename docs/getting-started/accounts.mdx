## Who can use a Jsint instance

Jsint is multi-user, but access is **approval-based**. Registering does not give
you access on its own: an administrator has to approve the account first.

Every account has a **status**:

| Status | Meaning |
|---|---|
| `pending` | Registered, waiting for an administrator. Sign-in returns `403 Account pending approval by an administrator`. |
| `active` | Approved. Full access to the UI, graphs, enrichers and the vault. |
| `suspended` | Blocked by an administrator. Sign-in and every API call are refused. |

This is separate from the **per-investigation roles** (`owner`, `admin`,
`editor`, `viewer`) that decide who may see or edit one case. Status decides
whether you may use the instance at all; roles decide what you may touch inside
it.

## Registering

1. Open `/register` and fill in username, email and password.
2. The account is created as `pending` and the page tells you an administrator
   must approve it.
3. Once approved, sign in normally at `/login`.

Nothing else is required from the new user — the administrator can also create
the account for them and hand over the credentials.

## Becoming an administrator

An account is an administrator when one of these applies:

- it was the **first account registered** on a fresh installation (this keeps a
  new deployment from locking itself out), or
- its address is listed in the **`ADMIN_EMAILS`** environment variable:

```bash
# .env — comma separated
ADMIN_EMAILS=you@example.com,teammate@example.com
```

A listed address is promoted to an active administrator the next time it
registers or signs in, so setting the variable is also the way to recover
administrator access on an existing installation.

## The admin dashboard

Administrators get an extra entry in the sidebar: **Administration**
(`/dashboard/admin`).

It shows:

- **counters** — total accounts, how many are awaiting approval, how many
  administrators exist;
- a **table of every account** with its email, role, status, creation date and
  how many **cases** it owns (investigations, with sketches and analyses).

From the table an administrator can:

| Action | Effect |
|---|---|
| **New user** | Create an account directly — it is approved immediately. |
| **Approve** | Move a `pending` account to `active`, letting it sign in. |
| **Suspend / Reactivate** | Block or restore an account; a suspended account is refused on every request, even with a valid token. |
| **Grant / remove administrator** | Promote a user to administrator or demote one. |
| **Reset password** | Set a new password for an account (there is no self-service reset mail). |
| **Delete** | Remove the account **and everything it owns**: cases, sketches, analyses, chats, vault keys, custom types, plus its graph data in Neo4j. |

Two guard rails prevent locking the deployment out: you cannot change your own
role or status, and the last remaining administrator cannot be demoted,
suspended or deleted.

## Notes for operators

- The approval flow is enforced by the API (`/api/admin/*` requires
  `is_admin`), not just by the UI — a non-admin calling those endpoints gets
  `403 Administrator privileges required`.
- Suspension takes effect immediately: the account status is re-checked on
  every request, so an existing session stops working.
- There is no email delivery, so approvals and password resets are manual by
  design. Point new users at the administrator (or create their account
  yourself).
